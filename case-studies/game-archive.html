Case Study

Game Archive

Rebuilding a collection of browser mini-games around one browse-and-play loop, so a new player starts playing in a single click instead of hunting through a menu.

Role Product Design & Front-End
Tools Figma, HTML, CSS, JavaScript
Timeline Ongoing
Scope UI system, interaction design, build

The problem

Game Archive started as a personal project to recreate the feeling of old game compilations. The games themselves worked, but each one had grown its own layout, its own button styles, and its own idea of where the player was.

The result was a collection that felt assembled rather than designed. Switching between games meant relearning the interface, and adding a new game meant designing a new interface with it. That cost was the real problem — not any single screen, but the fact that nothing carried over.

Approach

I treated the archive itself as the product and the games as content. That reframing let me design the container first, so each new game only had to describe itself rather than design an interface from scratch.

  1. Audit

    Catalogued every screen and control across the five games and grouped them by the job they were doing, not the game they belonged to.

  2. System

    Built one card, one panel, and one control set in Figma, then rebuilt every game on top of it without touching game logic.

  3. Verify

    Tested the flow on people who had never seen the project and watched where they hesitated, then cut everything they didn't need.

Key design decisions

One loop, not one menu. The landing view is the playable state. Tapping a card opens the game in place, and returning puts the player back exactly where they were in the grid. There is no separate "play" screen to navigate through.

State lives on the card. Each tile carries its own category, title, and progress state, so a player can tell what's already been tried without opening anything. The archive became browsable instead of a list of links.

Legacy on purpose. The visual language is retro, but the interaction model is not. Everything is keyboard reachable, every control has a visible focus state, and no interaction depends on hover alone.

Outcome

All five games now share one interface, which means a new game is a content addition rather than a design project. The archive has grown to include new entries without any of them needing a layout of their own.

What I'd do next

The system works for five games, but it has not been pressure-tested at twenty. Before scaling up I would add a lightweight filter for category and play state, and I would check the card grid against a narrower viewport range — a three-column grid is the part of this design most likely to break.
